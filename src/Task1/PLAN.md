# Планирование: анализ, идентификация проблем и поиск решений

## 1. Контекст

Компания «Александрит» развивает онлайн-магазин ювелирных изделий и производство украшений на заказ. В системе есть три основных приложения:

* онлайн-магазин;
* CRM;
* MES.

После открытия API для B2B-партнёров нагрузка выросла, появились жалобы клиентов и партнёров на просроченные или потерянные заказы. Также операторы жалуются на медленную загрузку первой страницы MES.

Цель анализа — выявить проблемные места, предложить инициативы для улучшения архитектуры и определить приоритеты на ближайшие полгода.

---

## 2. Существующие и потенциальные проблемные места

### 2.1. Нет единого источника истины по заказу

Данные о заказе распределены между онлайн-магазином, CRM и MES. В Shop DB хранится информация о заказе с точки зрения клиента, в MES DB — информация о производстве, назначениях операторов и производственных статусах.

Из-за этого возможны проблемы:

* разные системы могут иметь разные статусы одного заказа;
* сложно понять актуальное состояние заказа;
* сложно расследовать инциденты;
* при сбое интеграции заказ может «зависнуть» между системами.

### 2.2. Риск потери заказов при асинхронной интеграции

CRM и MES взаимодействуют через RabbitMQ. В описании нет информации о:

* гарантиях доставки сообщений;
* dead letter queue;
* идемпотентности обработчиков;
* повторной обработке сообщений;
* мониторинге очередей;
* корреляционных идентификаторах;
* журнале событий заказа.

Это критично, потому что жалобы клиентов похожи на проблему потери или некорректной обработки событий.

### 2.3. MES перегружен ответственностями

MES API одновременно:

* рассчитывает стоимость изделия;
* показывает список заказов;
* назначает заказы операторам;
* управляет производственными статусами.

Расчёт стоимости может занимать от 2–3 до 30 минут. Это тяжёлая операция, которая может конкурировать за ресурсы с пользовательскими сценариями операторов.

### 2.4. Тяжёлый расчёт стоимости блокирует производственные сценарии

Расчёт стоимости зависит от количества полигонов в 3D-модели. После открытия API число расчётов выросло. Если расчёты выполняются на том же инстансе MES API, что и пользовательские запросы, это может приводить к деградации всей MES.

Последствия:

* операторы медленно видят список заказов;
* заказы поздно попадают в работу;
* новые B2B-заказы создают нагрузку на производственный контур;
* ухудшается время выполнения заказов.

### 2.5. Медленная первая страница MES

Операторам важно видеть новые заказы, потому что от этого зависит их оплата. Команда уже добавила фильтр по статусам и пагинацию, но это не помогло.

Возможные причины:

* нет подходящих индексов в MES DB;
* запрос строится по большому количеству статусов;
* сортировка по дате работает без индекса;
* страница считает агрегаты по всем заказам;
* в дашборде смешаны список заказов и аналитические данные;
* база используется одновременно на чтение и запись.

### 2.6. Один инстанс каждого приложения

Каждое приложение развёрнуто в одном экземпляре. Это создаёт риски:

* нет горизонтального масштабирования;
* нет отказоустойчивости;
* любой сбой инстанса приводит к недоступности приложения;
* нельзя отдельно масштабировать чтение, API и фоновые операции.

### 2.7. Один инстанс базы данных на чтение и запись

Базы данных имеют один инстанс, который обслуживает и чтение, и запись. При росте нагрузки это становится узким местом.

Особенно рискованно для MES DB, потому что там одновременно происходят:

* запись статусов;
* назначение заказов;
* чтение списков заказов;
* фильтрация;
* сортировка;
* возможно, построение дашбордов.

### 2.8. Нет описанного мониторинга и алертинга

В описании не указаны:

* метрики приложений;
* метрики RabbitMQ;
* метрики баз данных;
* централизованные логи;
* трассировка;
* алерты;
* бизнес-метрики по заказам.

Без наблюдаемости команда реагирует на проблемы уже после жалоб клиентов.

### 2.9. API для партнёров открыт без изоляции нагрузки

B2B-партнёры используют API, который приводит к росту заказов и расчётов стоимости. Не описаны:

* rate limit;
* квоты;
* отдельный контур обработки B2B;
* приоритизация B2C/B2B;
* backpressure;
* контракты API;
* мониторинг качества обслуживания партнёров.

Из-за этого внешние клиенты могут перегружать внутренние производственные системы.

### 2.10. Процесс релизов стал узким местом

QA вручную прогоняет E2E-сценарии. Если находятся high/highest баги, релиз блокируется. Раньше задержки были до месяца, сейчас задержки растут.

Проблемы:

* мало автоматизации тестирования;
* один QA становится bottleneck;
* ручной деплой в release и production;
* нет описанных canary/blue-green-подходов;
* крупные релизы копят много изменений.

### 2.11. Недостаток данных для управления производственным потоком

Компания знает, что производственные мощности позволяют двукратный рост, но проблемы всё равно есть. Значит узкое место, скорее всего, не в физическом производстве, а в ИТ-процессах:

* заказ не попадает вовремя в производство;
* заказ теряется между системами;
* оператор поздно видит новый заказ;
* статус заказа не синхронизируется;
* менеджер не видит реальное состояние заказа.

## 3. Инициативы для устранения проблем

### 3.1. Ввести сквозную наблюдаемость

Нужно добавить:

* централизованные логи;
* технические метрики приложений;
* метрики RabbitMQ;
* метрики баз данных;
* бизнес-метрики заказов;
* correlation ID для заказа;
* алерты по критическим состояниям.

Ключевые бизнес-метрики:

* количество заказов по статусам;
* время нахождения заказа в каждом статусе;
* количество заказов без движения больше N часов;
* количество ошибок обработки сообщений;
* глубина очередей RabbitMQ;
* время расчёта стоимости;
* количество просроченных заказов.

### 3.2. Провести аудит RabbitMQ-интеграции

Нужно проверить и доработать:

* durable queues;
* persistent messages;
* manual ack;
* retry policy;
* dead letter exchange / dead letter queue;
* идемпотентность consumer-ов;
* защиту от дублирующей обработки сообщений;
* журналирование событий;
* мониторинг глубины очередей.

Цель — исключить потерю заказов и сделать обработку сообщений контролируемой.

### 3.3. Ввести модель жизненного цикла заказа

Нужно формализовать:

* какие статусы существуют;
* какая система имеет право менять каждый статус;
* какие переходы разрешены;
* какие события публикуются при изменении статуса;
* что делать при ошибке перехода;
* где хранится история изменений.

Результатом может стать таблица переходов статусов и единая схема событий заказа.

### 3.4. Выделить расчёт стоимости в отдельный сервис или worker-контур

Расчёт стоимости не должен выполняться внутри основного MES API, который обслуживает операторов.

Целевое решение:

* отдельный Price Calculation Service;
* очередь задач на расчёт;
* отдельные worker-инстансы;
* возможность горизонтального масштабирования worker-ов;
* хранение результата расчёта;
* статус расчёта: pending / processing / calculated / failed.

Это изолирует тяжёлую CPU-bound-нагрузку от пользовательского интерфейса MES.

### 3.5. Оптимизировать первую страницу MES

Нужно отдельно проанализировать запросы к MES DB.

Вероятные действия:

* добавить индексы под фильтрацию по статусу и сортировку по дате создания;
* разделить список заказов и агрегированный дашборд;
* ограничить выборку только нужными полями;
* добавить cursor-based pagination;
* добавить read model для списка новых заказов;
* кэшировать агрегаты по статусам;
* вынести тяжёлые отчётные запросы из основной транзакционной БД.

### 3.6. Ввести read model для операторского дашборда

Для MES можно сделать отдельную read model, оптимизированную под сценарий операторов:

* новые заказы;
* заказы по статусам;
* сортировка по дате;
* быстрый захват заказа оператором;
* минимальный набор полей.

Read model может обновляться через события и использоваться только для чтения.

### 3.7. Горизонтально масштабировать критичные приложения

Нужно убрать ограничение «один инстанс приложения».

Минимально:

* масштабировать MES API;
* масштабировать Shop API;
* масштабировать CRM API;
* добавить load balancer;
* сделать приложения stateless;
* проверить хранение сессий и файлов вне приложения.

### 3.8. Масштабировать базы данных

Для БД стоит рассмотреть:

* read replica для тяжёлых чтений;
* индексы;
* connection pooling;
* мониторинг медленных запросов;
* архивацию старых заказов;
* разделение OLTP и аналитических запросов.

### 3.9. Защитить внешний API для партнёров

Для API пользователей нужно добавить:

* rate limiting;
* квоты по партнёрам;
* API gateway;
* ключи доступа;
* мониторинг ошибок по партнёрам;
* понятные статусы обработки;
* документацию API;
* идемпотентные ключи для создания заказов.

Это снизит риск перегрузки внутренних систем.

### 3.10. Автоматизировать регрессионное тестирование

QA хочет заниматься автоматизацией, поэтому нужно использовать это как точку роста.

Минимально:

* покрыть smoke-тестами критический путь заказа;
* покрыть E2E-сценарий B2C-заказа;
* покрыть E2E-сценарий B2B-заказа;
* добавить проверки статусов;
* запускать автотесты в release-окружении.

### 3.11. Улучшить CI/CD и релизный процесс

Нужно уменьшить задержки релизов.

Возможные меры:

* автоматический деплой в release;
* release checklist;
* feature flags;
* small batch releases;
* rollback-процедуры;
* blue-green или canary deployment для критичных сервисов;
* обязательные smoke-тесты после деплоя.

### 3.12. Нанять или привлечь специалистов

Потенциально нужны:

* backend-инженер для C# / MES;
* QA automation engineer;
* DevOps/SRE-инженер или усиление DevOps-функции;
* backend-инженер для интеграций и событийной архитектуры.

Обоснование: текущая команда небольшая, а одновременно нужно решать производительность, интеграции, надёжность, тестирование и инфраструктуру.

## 4. Приоритизация инициатив

### Приоритет 1. Наблюдаемость и диагностика

Без мониторинга команда не сможет точно понять, где ломается процесс заказа. Сейчас компания узнаёт о проблемах от клиентов и партнёров. Это недопустимо для бизнеса.

Эта инициатива должна быть первой, потому что она снижает неопределённость и помогает правильно приоритизировать остальные работы.

### Приоритет 2. Надёжность обработки заказов и RabbitMQ-интеграции

Основная бизнес-проблема — клиенты и партнёры не получают заказы. Поэтому нужно обеспечить надёжное прохождение заказа между системами.

Важно исключить:

* потерю сообщений;
* дубли заказов;
* зависшие статусы;
* некорректную последовательность событий.

### Приоритет 3. Оптимизация MES и выделение расчёта стоимости

MES сейчас является критичным узлом. Он нужен операторам, но одновременно выполняет тяжёлый расчёт стоимости. Это нужно разделить.

Расчёт стоимости лучше вынести в отдельный worker-контур или отдельный сервис, а интерфейс операторов оптимизировать отдельно.

### Приоритет 4. Оптимизация дашборда операторов

Это влияет на скорость взятия заказов в работу и мотивацию операторов. Если операторы поздно видят новые заказы, заказ позже попадает в производство.

### Приоритет 5. Защита B2B API

После открытия API нагрузка резко выросла. API нужно сделать управляемым: rate limit, квоты, идемпотентность, мониторинг, документация.

### Приоритет 6. Масштабирование приложений и баз данных

Горизонтальное масштабирование важно, но его нужно делать после диагностики и устранения очевидных архитектурных проблем. Иначе можно просто масштабировать неэффективную архитектуру.

### Приоритет 7. Автоматизация тестирования и улучшение CI/CD

Это важно для скорости поставки изменений. Но сначала нужно стабилизировать критичный поток заказов, потому что бизнес уже теряет контракты.

## 5. Целевая архитектура через полгода

Через полгода целевая архитектура должна быть не полностью «идеальной», а стабилизированной и готовой к дальнейшему росту.

Я вижу её так:

1. Заказ проходит через системы по формализованной событийной модели.
2. Для каждого заказа есть сквозной идентификатор и история событий.
3. RabbitMQ используется с надёжной доставкой, retry, DLQ и мониторингом.
4. Расчёт стоимости вынесен из основного MES API в отдельный worker-контур или отдельный Price Calculation Service.
5. MES API обслуживает операторские сценарии отдельно от тяжёлых расчётов.
6. Для операторского дашборда есть оптимизированная read model или хорошо оптимизированные запросы.
7. B2B API защищён rate limit-ами, квотами и идемпотентными ключами.
8. Критичные приложения можно масштабировать горизонтально.
9. Есть централизованные логи, метрики, алерты и дашборды.
10. Есть автоматизированные smoke/E2E-тесты для критического пути заказа.
11. Релизы стали меньше, безопаснее и быстрее.

## 6. Если выбрать только три инициативы на ближайшие полгода

Если бы была возможность выполнить только три пункта, я бы выбрал следующие.

### 1. Ввести сквозную наблюдаемость

Причина: сейчас компания не понимает проблему до конца. Без метрик и логов любые архитектурные изменения будут частично основаны на догадках.

Что должно появиться:

* correlation ID заказа;
* логи по всем переходам статусов;
* метрики RabbitMQ;
* метрики MES API;
* метрики расчёта стоимости;
* метрики БД;
* алерты по зависшим заказам;
* дашборд заказов по статусам.

Эта инициатива быстро даст бизнесу и команде прозрачность.

### 2. Сделать обработку заказов надёжной

Причина: основная боль бизнеса — потерянные и просроченные заказы. Нужно обеспечить контролируемый жизненный цикл заказа.

Что входит:

* аудит RabbitMQ;
* DLQ;
* retry;
* manual ack;
* идемпотентность обработчиков;
* журнал событий заказа;
* формальная модель статусов;
* обработка зависших заказов.

Это напрямую снижает количество жалоб и риск потери контрактов.

### 3. Вынести расчёт стоимости из MES API и оптимизировать операторский контур

Причина: MES — ключевая система для производства. Если MES тормозит, заказы не попадают вовремя в работу.

Что входит:

* отдельная очередь задач на расчёт;
* отдельные worker-ы для расчёта стоимости;
* возможность масштабировать расчёт отдельно;
* оптимизация первой страницы MES;
* индексы и read model для новых заказов;
* быстрый сценарий «взять заказ в работу».

Это разделяет тяжёлую вычислительную нагрузку и работу операторов.

---

## 7. Почему не выбираю в топ-3 остальные инициативы

Горизонтальное масштабирование приложений важно, но без понимания узких мест оно может не решить проблему. Если причина в медленных SQL-запросах, потерянных сообщениях или тяжёлом расчёте, добавление новых инстансов даст ограниченный эффект.

Автоматизация тестирования и CI/CD тоже важны, но это скорее ускорение поставки изменений. Сейчас главная проблема — операционная стабильность заказов и потеря контрактов.

Защита B2B API важна, но её стоит делать после базовой наблюдаемости и стабилизации обработки заказов. При этом часть мер, например rate limit и идемпотентные ключи, можно включить в инициативу по надёжности обработки заказов.

## 8. Итоговый план на полгода

### Месяц 1

* Ввести correlation ID.
* Настроить централизованные логи.
* Добавить базовые метрики приложений, БД и RabbitMQ.
* Сделать дашборд заказов по статусам.
* Найти основные точки потери или зависания заказов.

### Месяц 2

* Провести аудит RabbitMQ.
* Добавить DLQ и retry.
* Обеспечить идемпотентность обработки сообщений.
* Описать конечный автомат статусов заказа.
* Добавить алерты по зависшим заказам.

### Месяц 3

* Оптимизировать запросы первой страницы MES.
* Добавить необходимые индексы.
* Разделить список заказов и агрегированный дашборд.
* Подготовить read model для операторского сценария, если индексов недостаточно.

### Месяц 4

* Вынести расчёт стоимости в отдельный worker-контур.
* Добавить очередь задач на расчёт.
* Добавить статусы расчёта.
* Масштабировать worker-ы отдельно от MES API.

### Месяц 5

## 9. Основной вывод

Главная проблема архитектуры сейчас не только в производительности. Основная проблема — отсутствие управляемого и наблюдаемого жизненного цикла заказа.

Компания растёт, но архитектура всё ещё похожа на систему для меньшей нагрузки: один инстанс каждого приложения, один инстанс БД, тяжёлые операции внутри MES, недостаточная наблюдаемость и неочевидная надёжность асинхронных интеграций.

Поэтому в первую очередь нужно сделать поток заказа прозрачным, надёжным и изолировать тяжёлый расчёт стоимости от операторских сценариев.
