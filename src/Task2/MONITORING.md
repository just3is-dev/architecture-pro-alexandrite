# Выбор и настройка мониторинга в системе

# 1. Мотивация

В настоящий момент компания сталкивается со следующими проблемами:

* потеря заказов;
* длительная обработка заказов;
* жалобы B2C-клиентов;
* жалобы B2B-партнёров;
* медленная работа MES;
* потеря контрактов.

Сейчас основным источником информации является Яндекс Метрика. Она показывает поведение пользователей интернет-магазина, но не позволяет контролировать состояние внутренних систем, очередей сообщений, баз данных и производственного процесса.

Без мониторинга команда узнаёт о проблемах только после обращения клиентов или сотрудников компании.

Внедрение мониторинга позволит:

* быстрее обнаруживать проблемы;
* сократить время расследования инцидентов;
* предотвратить потерю заказов;
* понимать причины деградации производительности;
* прогнозировать необходимость масштабирования;
* принимать архитектурные решения на основе данных;
* контролировать выполнение SLA по заказам.

Таким образом, мониторинг позволит снизить количество потерянных заказов и уменьшить финансовые потери компании.

---

# 2. Выбор подхода к мониторингу

Для разных компонентов системы будут использоваться разные подходы.

## RED для API-сервисов

Подход RED подходит для пользовательских сервисов:

* Shop API
* CRM API
* MES API

Контролируются:

* Rate (нагрузка)
* Errors (ошибки)
* Duration (задержки)

Этот подход позволяет быстро понять, как пользователи воспринимают работу системы.

## USE для инфраструктурных компонентов

Подход USE применяется для:

* RabbitMQ
* PostgreSQL
* EC2-инстансов

Контролируются:

* Utilization
* Saturation
* Errors

Этот подход помогает обнаруживать инфраструктурные узкие места.

## Бизнесовый мониторинг

Для данной системы особенно важны бизнесовые метрики.

Главная проблема компании — не отказ сервера, а потерянный заказ.

Поэтому дополнительно необходимо отслеживать жизненный цикл заказа.

# 3. Метрики API

## Number of requests (RPS) for Shop API

Назначение:
Позволяет понимать текущую нагрузку на интернет-магазин.

Ярлыки:

* endpoint
* method
* status_code

---

## Number of requests (RPS) for CRM API

Назначение:
Контроль нагрузки со стороны продавцов и интеграций.

Ярлыки:

* endpoint
* method
* status_code

---

## Number of requests (RPS) for MES API

Назначение:
Позволяет отслеживать нагрузку операторов и расчётных процессов.

Ярлыки:

* endpoint
* method
* status_code

---

## Number of requests (RPS) per user

Для всех API.

Назначение:

Позволяет выявлять:

* злоупотребления API;
* аномальную активность пользователей;
* перегрузку со стороны отдельных B2B-партнёров.

Ярлыки:

* user_id
* api_key
* partner_id

---

## Response Time (Latency)

Для:

* Shop API
* CRM API
* MES API

Назначение:

Контроль пользовательского опыта.

Ярлыки:

* endpoint
* method
* status_code

Отслеживаем:

* p50
* p95
* p99

---

## Number of HTTP 500

Для всех API.

Назначение:

Позволяет быстро обнаружить ошибки приложения.

Ярлыки:

* endpoint
* exception_type

---

## Number of HTTP 200

Для всех API.

Назначение:

Используется совместно с HTTP 500 для расчёта процента успешных запросов.

---

## Number of simultaneous sessions

Для всех API.

Назначение:

Помогает оценивать фактическую активность пользователей.

---

# 4. Метрики RabbitMQ

## Number of messages in flight

Назначение:

Показывает количество сообщений, находящихся в обработке.

Ярлыки:

* queue
* consumer

---

## Number of dead-letter-exchange letters

Назначение:

Показывает количество сообщений, обработка которых завершилась ошибкой.

Критически важная метрика для текущего кейса.

Ярлыки:

* queue
* routing_key

---

## Дополнительные метрики RabbitMQ

### Queue Depth

Количество сообщений в очереди.

Позволяет понять:

* успевают ли обработчики обрабатывать поток заказов;
* есть ли накопление сообщений.

Ярлыки:

* queue

---

### Message Processing Time

Среднее время обработки сообщения.

Ярлыки:

* queue
* consumer

# 7. Бизнесовые метрики

Для данной системы они являются наиболее важными.

## Orders Created

Количество новых заказов.

Ярлыки:

* source (B2C, B2B)

---

## Orders Per Status

Количество заказов в каждом статусе.

Ярлыки:

* status

---

## Order Lead Time

Время от создания заказа до закрытия.

Позволяет контролировать SLA.

---

## Time In Status

Среднее время нахождения заказа в каждом статусе.

Ярлыки:

* status

---

## Orders Stuck In Status

Количество заказов, находящихся в статусе дольше допустимого времени.

Ярлыки:

* status

---

## Price Calculation Duration

Время расчёта стоимости изделия.

Ярлыки:

* model_complexity
* source

---

## Failed Order Processing

Количество заказов, завершившихся ошибкой.

# 9. Показатели насыщенности

## MES API CPU

Порог:

* Warning: 70%
* Critical: 90%

Действия:

* создание тикета;
* уведомление DevOps;
* масштабирование инстанса.

---

## Queue Depth RabbitMQ

Порог:

* более 1000 сообщений в очереди.

Действия:

* уведомление команды;
* анализ производительности consumer-ов;
* масштабирование обработчиков.

---

## Time In Status

Порог:

* заказ находится в статусе более 24 часов сверх ожидаемого времени.

Действия:

* создание инцидента;
* уведомление ответственного менеджера.

---

## Dead Letter Queue

Порог:

* любое значение больше 0.

Действия:

* немедленное уведомление команды;
* анализ причины отказа;
* повторная обработка сообщений.

---

## DB Connections

Порог:

* 80% от максимально допустимого количества соединений.

Действия:

* создание предупреждения;
* анализ connection pool;
* масштабирование базы данных.

---

# Вывод

Основная цель мониторинга — сделать поток заказов полностью наблюдаемым. Для компании критично не только контролировать инфраструктуру, но и видеть прохождение каждого заказа через все стадии обработки. Поэтому наряду с техническими метриками особое внимание должно уделяться бизнесовым метрикам жизненного цикла заказа.
