# Архитектурное решение по трейсингу

## 1. Системы, которые необходимо покрыть трейсингом

Трейсингом необходимо покрыть все компоненты, через которые проходит заказ:

* Internet Shop;
* Shop API;
* CRM;
* CRM API;
* MES;
* MES API;
* RabbitMQ;
* S3-хранилище 3D-файлов;
* Shop DB;
* MES DB.

Особенно важные точки отказа:

* загрузка 3D-файла;
* создание заказа в Shop API;
* сохранение заказа в Shop DB;
* публикация события в RabbitMQ;
* получение сообщения CRM API или MES API;
* расчёт стоимости в MES API;
* изменение статуса заказа;
* назначение заказа оператору;
* запись производственного статуса в MES DB.

---

## 2. Данные, которые должны попадать в трейсинг

В трейсинг должны попадать:

* trace_id;
* span_id;
* parent_span_id;
* correlation_id;
* order_id;
* customer_id или partner_id;
* source: B2C / B2B;
* current_status;
* next_status;
* event_type;
* message_id;
* queue_name;
* routing_key;
* retry_count;
* HTTP method;
* HTTP endpoint;
* HTTP status code;
* request duration;
* service name;
* service version;
* environment;
* error type;
* error message;
* timestamp;
* model_file_id;
* price_calculation_duration.

Персональные данные клиента в трейсинг передавать нельзя. Вместо email, телефона и ФИО нужно использовать технические идентификаторы.

---

## 3. Мотивация

Сейчас заказы могут находиться в непонятном состоянии или зависать между системами. Команда не видит полную цепочку обработки заказа и вынуждена расследовать проблемы по отдельным логам разных сервисов.

Трейсинг нужен, чтобы по одному order_id или correlation_id увидеть весь путь заказа:

1. создание заказа;
2. загрузка 3D-файла;
3. отправка события;
4. получение события другим сервисом;
5. расчёт стоимости;
6. изменение статуса;
7. передача заказа в производство;
8. завершение заказа.

Это позволит:

* быстрее находить место сбоя;
* понимать, где заказ завис;
* выявлять потерянные сообщения;
* сокращать время расследования инцидентов;
* снижать количество просроченных заказов;
* уменьшать количество жалоб клиентов и партнёров.

Метрики, на которые повлияет внедрение трейсинга:

* MTTR — среднее время восстановления после инцидента;
* количество заказов в неизвестном состоянии;
* количество зависших заказов;
* среднее время прохождения заказа между статусами;
* количество обращений клиентов по потерянным заказам;
* процент успешной обработки заказов;
* время расчёта стоимости изделия.

---

## 4. Предлагаемое решение

Для реализации трейсинга предлагается использовать OpenTelemetry.

Компоненты решения:

* OpenTelemetry SDK в Shop API;
* OpenTelemetry SDK в CRM API;
* OpenTelemetry SDK в MES API;
* OpenTelemetry Collector;
* Jaeger или Grafana Tempo как backend для хранения трейсов;
* Grafana или Jaeger UI для просмотра трейсов.

### Как будет работать трейсинг

При создании заказа Shop API создаёт trace_id и correlation_id. Эти идентификаторы передаются дальше:

* в HTTP-запросах через traceparent header;
* в RabbitMQ-сообщениях через message headers;
* в логах сервисов;
* в событиях изменения статуса заказа.

Если заказ создаётся через B2B API, MES API также должен создавать или принимать correlation_id.

Для каждого важного действия создаётся отдельный span:

* create_order;
* upload_3d_file;
* save_order_to_db;
* publish_order_event;
* consume_order_event;
* calculate_price;
* update_order_status;
* assign_order_to_operator;
* complete_manufacturing.

Для RabbitMQ нужно передавать trace context в заголовках сообщения. Тогда цепочка не будет разрываться между producer и consumer.

## 5. Автоматический мониторинг процесса прохождения заказа и алертинг

Дополнительно можно реализовать автоматический контроль зависших заказов.

Для этого добавляется компонент Order Process Monitor.

Он будет регулярно проверять данные о прохождении заказов и находить ситуации:

* заказ слишком долго находится в одном статусе;
* заказ был создан, но не попал в CRM;
* заказ был создан, но не попал в MES;
* расчёт стоимости не завершился;
* сообщение попало в DLQ;
* статус заказа не изменялся дольше допустимого времени.

При обнаружении проблемы Order Process Monitor отправляет событие в Alertmanager. Alertmanager уведомляет:

* поддержку;
* DevOps-инженера;
* тимлида;
* менеджеров продаж при бизнес-критичных заказах.

## 6. Компромиссы

Трейсинг не решит проблему сам по себе. Он помогает находить причины, но не исправляет архитектурные дефекты автоматически.

Ограничения:

* если сервис не инструментирован, цепочка трейса будет неполной;
* если RabbitMQ-сообщения не передают trace context, трейс будет разрываться;
* если в старом коде MES сложно добавить OpenTelemetry, потребуется дополнительная разработка;
* трейсинг создаёт дополнительную нагрузку на приложения;
* хранение большого количества трейсов требует ресурсов;
* слишком подробный трейсинг может стать дорогим.

Чтобы снизить стоимость, можно использовать sampling:

* 100% трейсов для ошибок;
* 100% трейсов для заказов с долгим временем обработки;
* 10–20% успешных заказов;
* 100% трейсов для B2B-заказов на первом этапе после внедрения.

## 7. Безопасность

Система трейсинга должна быть доступна только сотрудникам компании.

Меры безопасности:

* доступ к Grafana / Jaeger UI только через корпоративную сеть или VPN;
* обязательная аутентификация;
* разграничение ролей;
* доступ для поддержки только на чтение;
* доступ администраторов только для DevOps и тимлида;
* запрет на запись персональных данных в трейсы;
* маскирование email, телефона, ФИО и адресов;
* хранение трейсов ограниченное время, например 14–30 дней;
* TLS для передачи данных между сервисами и OpenTelemetry Collector;
* аудит доступа к системе трейсинга.

---

## 8. Итог

Трейсинг позволит сделать путь заказа прозрачным от момента создания до завершения производства. Для текущей ситуации это критично, потому что компания теряет заказы и контракты не из-за отсутствия Яндекс Метрики, а из-за непрозрачности внутренних процессов.

Главная цель решения — дать команде возможность быстро ответить на вопросы:

* где сейчас заказ;
* какой сервис обработал заказ последним;
* какое сообщение потерялось или не обработалось;
* сколько времени заказ провёл на каждом этапе;
* почему заказ не дошёл до производства.
