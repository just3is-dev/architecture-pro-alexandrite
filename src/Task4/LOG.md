# Архитектурное решение по логированию

## 1. Контекст

Компания «Александрит» сталкивается с проблемами при обработке заказов:

* заказы зависают в непонятных состояниях;
* клиенты и партнёры жалуются на потерянные или просроченные заказы;
* поддержка разбирает инциденты со слов клиентов;
* разработчикам сложно быстро понять, что произошло внутри системы.

Для решения этой проблемы нужно внедрить централизованное структурированное логирование.

---

## 2. Системы, из которых нужно собирать логи

Логи нужно собирать из всех систем, участвующих в жизненном цикле заказа:

* Internet Shop;
* Shop API;
* CRM;
* CRM API;
* MES;
* MES API;
* RabbitMQ;
* PostgreSQL Shop DB;
* PostgreSQL MES DB;
* S3-хранилище 3D-моделей;
* API Gateway для B2B API, если он будет добавлен.

В первую очередь логирование нужно внедрить в:

1. Shop API;
2. CRM API;
3. MES API;
4. RabbitMQ consumers/producers.

Именно через эти компоненты проходит заказ, и именно там наиболее вероятны потери сообщений, ошибки статусов и зависания обработки.

---

## 3. Какие логи нужно собирать

Логи должны быть структурированными, в JSON-формате.

Обязательные поля для всех логов:

* timestamp;
* level;
* service;
* environment;
* version;
* trace_id;
* span_id;
* correlation_id;
* order_id;
* user_id или partner_id;
* source: B2C / B2B;
* event_type;
* message;
* duration_ms;
* error_code;
* error_message.

Персональные данные клиента не должны попадать в логи в открытом виде.

---

## 4. Логи уровня INFO

INFO используется для бизнес-событий и штатных технических событий.

### Создание заказа

Логируем:

* timestamp;
* order_id;
* customer_id или partner_id;
* source;
* current_status;
* event_type = order_created.

### Загрузка 3D-модели

Логируем:

* timestamp;
* order_id;
* model_file_id;
* file_size;
* source;
* event_type = model_uploaded.

### Отправка заказа на расчёт стоимости

Логируем:

* timestamp;
* order_id;
* message_id;
* queue_name;
* event_type = price_calculation_requested.

### Получение сообщения из RabbitMQ

Логируем:

* timestamp;
* order_id;
* message_id;
* queue_name;
* retry_count;
* event_type = message_consumed.

### Успешный расчёт стоимости

Логируем:

* timestamp;
* order_id;
* price;
* calculation_duration_ms;
* event_type = price_calculated.

### Изменение статуса заказа

Логируем:

* timestamp;
* order_id;
* previous_status;
* new_status;
* actor_type;
* actor_id;
* event_type = order_status_changed.

### Назначение заказа оператору

Логируем:

* timestamp;
* order_id;
* operator_id;
* event_type = order_assigned.

### Завершение производства

Логируем:

* timestamp;
* order_id;
* operator_id;
* event_type = manufacturing_completed.

### Отправка заказа покупателю

Логируем:

* timestamp;
* order_id;
* delivery_id;
* event_type = order_shipped.

### Закрытие заказа

Логируем:

* timestamp;
* order_id;
* close_reason;
* event_type = order_closed.

## 5. Другие уровни логирования

### DEBUG

Используется только в dev/release окружениях или временно при расследовании инцидента.

Примеры:

* параметры внутренних вычислений;
* детали маршрутизации сообщения;
* технические детали обработки 3D-модели.

В production DEBUG по умолчанию выключен.

### WARN

Используется для нестандартных ситуаций, которые не сломали процесс, но требуют внимания.

Примеры:

* повторная обработка сообщения;
* превышение ожидаемого времени расчёта;
* заказ находится в статусе дольше допустимого времени;
* внешний API вернул нестабильный ответ;
* превышение лимита запросов партнёром.

### ERROR

Используется для ошибок, из-за которых операция не была выполнена.

Примеры:

* ошибка сохранения заказа;
* ошибка публикации сообщения в RabbitMQ;
* ошибка обработки сообщения;
* ошибка расчёта стоимости;
* ошибка изменения статуса заказа;
* ошибка загрузки файла из S3.

### FATAL

Используется для критических ошибок, из-за которых сервис не может продолжать работу.

Примеры:

* сервис не может подключиться к базе данных;
* сервис не может подключиться к RabbitMQ;
* приложение не может стартовать из-за некорректной конфигурации.

---

## 6. Мотивация

Сейчас поддержка и разработчики тратят много времени на расследование инцидентов, потому что информация о проблемах находится в разных системах и часто восстанавливается со слов клиента.

Централизованное логирование позволит:

* быстро находить события по order_id;
* видеть историю изменений статусов заказа;
* понимать, какой сервис обработал заказ последним;
* видеть ошибки RabbitMQ, MES и CRM в одном месте;
* снизить нагрузку на поддержку;
* ускорить расследование инцидентов;
* уменьшить количество потерянных заказов;
* повысить доверие B2B-партнёров.

Метрики, на которые повлияет внедрение логирования:

* MTTR — среднее время расследования и восстановления после инцидента;
* количество обращений в поддержку по потерянным заказам;
* количество заказов в неизвестном состоянии;
* количество повторно открытых инцидентов;
* процент заказов, обработанных без ручного вмешательства.

---

## 7. Что внедрять в первую очередь

Команда не сможет сразу внедрить логирование и трейсинг во всех системах. Поэтому приоритет должен быть таким.

### Приоритет 1. MES API

MES отвечает за расчёт стоимости и производственные статусы. Сейчас именно в MES видны проблемы с производственным процессом и медленной работой интерфейса операторов.

### Приоритет 2. CRM API

CRM участвует в подтверждении заказа и работе продавцов. Если заказ не попал в CRM или статус не изменился, менеджеры не смогут корректно работать с клиентом.

### Приоритет 3. Shop API

Shop API создаёт B2C-заказы, принимает 3D-модели и запускает процесс обработки заказа.

### Приоритет 4. RabbitMQ producers/consumers

Нужно логировать публикацию, получение, повторную обработку и ошибки обработки сообщений. Это особенно важно, потому что сообщения могут теряться или попадать в некорректное состояние.

### Приоритет 5. B2B API

После открытия API появились проблемы с партнёрами. Нужно логировать запросы партнёров, rate limit, ошибки создания заказов и идемпотентные ключи.

---

## 8. Предлагаемое решение

Предлагается внедрить централизованное логирование на базе OpenSearch Stack:

* OpenSearch — хранение и поиск логов;
* OpenSearch Dashboards — интерфейс для поиска и анализа;
* Fluent Bit — агент сбора логов с EC2/Kubernetes;
* структурированные JSON-логи в приложениях;
* correlation_id для связи логов между системами;
* trace_id для связи логов с трейсингом.

Схема решения:

* приложения пишут структурированные JSON-логи в stdout или log-файлы;
* Fluent Bit собирает логи;
* Fluent Bit отправляет логи в OpenSearch;
* OpenSearch хранит логи в отдельных индексах;
* OpenSearch Dashboards используется поддержкой и разработчиками для расследования инцидентов.

Логи должны быть связаны с трейсингом через поля:

* trace_id;
* span_id;
* correlation_id;
* order_id.

Это позволит из трейса перейти к логам конкретного заказа.

## 9. Новые компоненты на C4-схеме

На схему нужно добавить:

* Fluent Bit Agent;
* OpenSearch;
* OpenSearch Dashboards;
* Alerting Rules;
* Notification Channel.

Новые связи:

* Shop API → Fluent Bit;
* CRM API → Fluent Bit;
* MES API → Fluent Bit;
* RabbitMQ consumers/producers → Fluent Bit;
* Fluent Bit → OpenSearch;
* OpenSearch Dashboards → OpenSearch;
* Alerting Rules → Notification Channel.

Новые элементы на схеме следует выделить красным цветом.

## 10. Политика безопасности

В логах запрещено хранить в открытом виде:

* ФИО клиента;
* email;
* телефон;
* адрес доставки;
* платёжные данные;
* содержимое файлов 3D-моделей;
* токены;
* пароли;
* API keys.

Вместо персональных данных нужно использовать технические идентификаторы:

* customer_id;
* partner_id;
* order_id;
* model_file_id.

Доступ к логам:

* поддержка — только чтение и только бизнесовые поля;
* разработчики — чтение технических логов;
* DevOps — администрирование логовой платформы;
* менеджеры — доступ только к бизнесовым дашбордам без технических деталей;
* внешним пользователям доступ запрещён.

Дополнительные меры:

* аутентификация через корпоративную учётную запись;
* разграничение ролей;
* аудит доступа к логам;
* TLS для передачи логов;
* маскирование чувствительных данных;
* отдельные индексы для production, release и dev;
* запрет DEBUG-логов в production без отдельного согласования.

---

## 11. Политика хранения логов

Предлагается использовать отдельные индексы:

* logs-shop-api-prod-*;
* logs-crm-api-prod-*;
* logs-mes-api-prod-*;
* logs-rabbitmq-prod-*;
* logs-b2b-api-prod-*;
* logs-system-prod-*.

Сроки хранения:

* ERROR и WARN — 90 дней;
* INFO — 30 дней;
* DEBUG — 7 дней;
* audit logs — 180 дней.

Для экономии места:

* использовать index lifecycle policy;
* архивировать старые индексы;
* ограничить размер одного индекса;
* не логировать большие payload;
* не логировать бинарные данные и содержимое 3D-файлов.

---

## 12. Превращение сбора логов в систему анализа логов

Просто собирать логи недостаточно. Нужно настроить правила анализа и алертинга.

### Алертинг

Нужно настроить алерты:

* рост количества ERROR в MES API;
* рост количества ERROR в CRM API;
* сообщения попадают в DLQ;
* резкий рост количества заказов от одного партнёра;
* заказ не меняет статус дольше допустимого времени;
* расчёт стоимости завершается ошибкой;
* ошибка подключения к RabbitMQ;
* ошибка подключения к базе данных.

### Поиск аномалий

Нужно отслеживать:

* резкий рост количества заказов;
* резкий рост запросов от одного партнёра;
* всплеск HTTP 500;
* большое количество повторных сообщений;
* всплеск ошибок загрузки 3D-файлов;
* всплеск длительных расчётов стоимости.

Пример:

Если обычно создаётся 4 заказа в секунду, а за секунду стало 10 000, система должна:

1. создать критический алерт;
2. уведомить DevOps и тимлида;
3. временно включить rate limit для B2B API;
4. при необходимости ограничить подозрительного партнёра.

## 14. Обоснование выбора

Для «Александрита» предлагается использовать OpenSearch Stack.

Причины:

* хорошо подходит для структурированных JSON-логов;
* поддерживает быстрый поиск по order_id, trace_id, correlation_id;
* позволяет строить дашборды;
* поддерживает алертинг;
* имеет открытую лицензию;
* хорошо интегрируется с Fluent Bit;
* дешевле, чем Splunk;
* функционально ближе к ELK, но с меньшими лицензионными рисками.

Grafana Loki тоже можно рассмотреть, особенно если компания будет активно использовать Grafana для метрик и трейсов. Но для текущей задачи важен поиск по множеству структурированных полей, поэтому OpenSearch выглядит более подходящим выбором.

---

## 15. Итог

Логирование должно стать основой для расследования инцидентов и поддержки клиентов.

Главный принцип решения:

* каждый значимый шаг заказа логируется;
* все логи имеют order_id, correlation_id и trace_id;
* логи собираются централизованно;
* чувствительные данные маскируются;
* по логам строятся алерты и бизнесовые дашборды.

Это позволит компании быстрее разбирать проблемы, снижать нагрузку на поддержку и уменьшать количество потерянных заказов.
