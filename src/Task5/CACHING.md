# Архитектурное решение по кешированию

## 1. Контекст

В системе «Александрит» есть проблема с производительностью MES. Операторы жалуются, что первая страница MES долго загружается. На этой странице отображается список заказов в работе по статусам. Команда уже добавила фильтр по статусам и пагинацию, но это не помогло.

Также новых клиентов не устраивает скорость выполнения заказа. Судя по описанию системы, производственные мощности позволяют справиться с ростом, поэтому проблема, скорее всего, находится не в физическом производстве, а в ИТ-контуре: заказы поздно появляются у операторов, долго загружаются в MES или задерживаются на этапах обработки.

---

## 2. Что имеет смысл кешировать

Кешировать имеет смысл не весь MES, а конкретные read-heavy сценарии:

1. Список новых заказов для операторов.
2. Список заказов по статусам.
3. Первую страницу операторского дашборда.
4. Агрегаты по количеству заказов в статусах.
5. Метаданные заказа, которые часто читаются и редко меняются.

Не следует кешировать:

* саму операцию изменения статуса заказа;
* назначение заказа оператору;
* расчёт стоимости изделия;
* критичные транзакционные операции;
* данные, где недопустимо показывать устаревшее состояние.

Основной кандидат на кеширование — чтение списка заказов в MES.

---

## 3. Мотивация

Кеширование нужно внедрить, чтобы решить следующие проблемы:

* снизить время загрузки первой страницы MES;
* уменьшить нагрузку на MES DB;
* ускорить отображение новых заказов операторам;
* снизить количество медленных SQL-запросов;
* уменьшить конкуренцию между чтением списка заказов и записью статусов;
* повысить стабильность MES при росте количества заказов.

Для бизнеса это даст:

* операторы быстрее берут заказы в работу;
* заказы меньше времени проводят в ожидании;
* снижается риск просрочки заказа;
* уменьшается количество жалоб клиентов;
* снижается вероятность потери B2B-контрактов.

---

## 4. Предлагаемое решение

Предлагается внедрить серверное кеширование в MES API с использованием Redis.

Кеширование будет применяться к операции чтения списка заказов:

```text
GET /orders?status=...&page=...&limit=...
```

Для операции изменения статуса заказа кеш не будет использоваться как источник истины. Изменение статуса всегда записывается в MES DB.

Выбранный подход:

* серверное кеширование;
* Redis как отдельное кеш-хранилище;
* паттерн Cache-Aside;
* инвалидация по ключу при изменении статуса заказа;
* короткий TTL как дополнительная страховка.

---

## 5. Почему серверное кеширование

Клиентское кеширование здесь подходит хуже, потому что операторам важно видеть актуальные новые заказы. Если кешировать данные в браузере, разные операторы могут видеть разные версии списка, а это критично для бизнес-процесса: кто первым взял заказ, тот получает оплату.

Серверное кеширование лучше, потому что:

* кеш общий для всех операторов;
* инвалидацию контролирует MES API;
* проще обеспечить единые правила актуальности;
* можно централизованно сбрасывать кеш при изменении статуса;
* можно контролировать TTL и ключи кеша;
* можно собирать метрики hit/miss.

---

## 6. Выбор паттерна кеширования

### Выбранный паттерн: Cache-Aside

При чтении списка заказов MES API сначала обращается в Redis.

Если данные есть в кеше:

1. MES API возвращает список заказов из Redis.
2. MES DB не нагружается.

Если данных нет в кеше:

1. MES API читает данные из MES DB.
2. MES API записывает результат в Redis.
3. MES API возвращает данные оператору.

При изменении статуса заказа:

1. MES API записывает изменение в MES DB.
2. MES API инвалидирует связанные ключи в Redis.
3. Следующее чтение снова загрузит актуальные данные из MES DB.

### Почему Cache-Aside подходит

Cache-Aside подходит, потому что:

* список заказов — это read-heavy сценарий;
* источник истины остаётся в MES DB;
* кеш можно внедрить без полной перестройки архитектуры;
* приложение само контролирует, какие данные кешировать;
* при сбое Redis система может продолжить работать через MES DB.

---

## 7. Почему не Write-Through

Write-Through означает, что при записи данные одновременно записываются в БД и кеш.

Для текущего сценария это хуже, потому что:

* изменение статуса заказа затрагивает сразу несколько списков: старый статус, новый статус, общий дашборд, агрегаты;
* легко получить сложную и ошибочную логику обновления нескольких кеш-ключей;
* запись становится более сложной;
* кеш начинает играть слишком важную роль в write-path;
* повышается риск рассинхронизации.

Для статусов заказа надёжнее записывать статус в БД, а кеш инвалидировать.

---

## 8. Почему не Refresh-Ahead

Refresh-Ahead заранее обновляет кеш до истечения TTL.

Для текущего сценария это не лучший первый вариант, потому что:

* новые заказы появляются динамически;
* операторам важна актуальность;
* сложно заранее предсказать, какие фильтры и страницы будут нужны;
* можно создавать лишнюю нагрузку на MES DB;
* решение сложнее в реализации.

Refresh-Ahead можно рассмотреть позже для агрегатов дашборда, если будут понятные стабильные запросы.

---

## 9. Стратегия инвалидации кеша

Предлагается комбинированная стратегия:

1. Инвалидация по ключу при изменении статуса.
2. TTL как страховка от устаревших данных.
3. Версионирование ключей для массовой инвалидации.

### Инвалидация по ключу

При изменении статуса заказа нужно удалить ключи, связанные с:

* предыдущим статусом;
* новым статусом;
* первой страницей дашборда;
* агрегатами по статусам.

Например, если заказ перешёл из `PRICE_CALCULATED` в `MANUFACTURING_STARTED`, нужно инвалидировать:

```text
mes:orders:list:status:PRICE_CALCULATED:page:1
mes:orders:list:status:MANUFACTURING_STARTED:page:1
mes:orders:dashboard:statuses
```

### TTL

Для списков заказов:

```text
TTL = 30 секунд
```

Для агрегатов по статусам:

```text
TTL = 10–30 секунд
```

TTL нужен как защита на случай, если программная инвалидация не сработает.

### Почему не только TTL

Только TTL не подходит, потому что операторам важно видеть новые заказы быстро. Если поставить TTL 5 минут, оператор может долго видеть устаревший список. Если поставить TTL 5 секунд, польза кеша будет небольшой.

Поэтому TTL используется только как дополнительная страховка, а основная стратегия — инвалидация по ключу.

---

## 10. Ключи кеша

Примеры ключей:

```text
mes:orders:list:status:{status}:page:{page}:limit:{limit}:sort:{sort}
mes:orders:dashboard:statuses
mes:orders:summary:status:{status}
```

Для первой страницы:

```text
mes:orders:list:status:PRICE_CALCULATED:page:1:limit:50:sort:created_at_desc
```

---

## 11. Сравнение стратегий

| Стратегия      | Плюсы                                                                                                       | Минусы                                                                          | Итог                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------- |
| Cache-Aside    | Простая реализация, БД остаётся источником истины, можно внедрять постепенно, отказ Redis не ломает систему | Возможен cache miss, нужна инвалидация                                          | Лучший вариант для первого этапа        |
| Write-Through  | Кеш обновляется при записи, меньше cache miss                                                               | Сложная запись, риск рассинхронизации нескольких списков, усложнение write-path | Не подходит для статусов заказа         |
| Refresh-Ahead  | Может давать быстрые ответы на популярные запросы                                                           | Сложнее реализация, сложно предсказать нужные фильтры, риск лишней нагрузки     | Можно рассмотреть позже для агрегатов   |
| Только TTL     | Просто реализовать                                                                                          | Возможны устаревшие данные, слабый контроль актуальности                        | Недостаточно для операторского сценария |
| Клиентский кеш | Быстро для одного пользователя                                                                              | Разные операторы видят разные данные, сложная инвалидация                       | Не подходит как основное решение        |

---

## 12. Риски и ограничения

### Устаревшие данные

Кеш может вернуть устаревший список заказов. Для снижения риска используется инвалидация по ключу и короткий TTL.

### Cache stampede

Если кеш одновременно истёк у популярного ключа, много запросов может пойти в БД. Для снижения риска можно добавить lock на пересчёт кеша или stale-while-revalidate.

### Конкуренция операторов

Даже если список кешируется, операция «взять заказ в работу» должна быть атомарной в MES DB. Нельзя полагаться на кеш при назначении заказа.

Нужно использовать:

* транзакцию;
* optimistic locking или conditional update;
* проверку текущего статуса в БД.

Например:

```sql
UPDATE orders
SET status = 'MANUFACTURING_STARTED', operator_id = :operatorId
WHERE id = :orderId
  AND status = 'PRICE_CALCULATED';
```

Если обновлено 0 строк, значит заказ уже взял другой оператор.

### Отказ Redis

Если Redis недоступен, MES API должен читать данные напрямую из MES DB. Это ухудшит производительность, но не должно ломать основной сценарий.

---

## 13. Метрики кеширования

Нужно отслеживать:

* cache hit ratio;
* cache miss ratio;
* latency чтения списка заказов;
* количество запросов к MES DB;
* количество invalidation events;
* Redis memory usage;
* Redis errors;
* время выполнения SQL-запросов к списку заказов.

---

## 14. Итоговое решение

Для MES предлагается внедрить серверное кеширование через Redis по паттерну Cache-Aside.

Кешируется только чтение списка заказов и агрегаты дашборда. Запись статусов всегда выполняется в MES DB, после чего связанные ключи кеша инвалидируются.

Такой подход позволяет:

* ускорить первую страницу MES;
* снизить нагрузку на MES DB;
* сохранить MES DB как источник истины;
* не усложнять критичный write-path;
* постепенно внедрить кеширование без полной перестройки архитектуры.
